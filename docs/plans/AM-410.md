# AM-410 · Akcje sesji: x stop, Zatrzymaj i Respawn w panelu i palecie

Issue: #88 · Wymagania: FR-K2 (część: x), FR-S4 (stop, respawn), FR-K1 · ENG-I2, ENG-I4, ENG-C8, ENG-C10, ENG-T4 · docs/05 „Panel szczegółów”, „Skróty klawiszowe” · ADR 0011 (przyjęta) · Zależy: AM-409

## Zakres

`sessions:api` ma już wszystkie potrzebne operacje (`SessionCommands.stop`, `respawn`, `remove`; AM-404), więc zadanie nie zmienia `api` żadnego feature. Szacunek całości (stop, respawn, usuwanie z dialogiem) to ok. 410 linii z zapasem, czyli więcej niż limit ENG-C10. Dlatego ten plan dzieli zadanie (pytanie blokujące 1):

1. **`mission-control:ui`**: intencje `StopSelected` i `RespawnSelected`, publiczny stan `actions`, przyciski „Zatrzymaj” i „Respawn” w panelu szczegółów, tekst „w toku” i stały komunikat błędu w panelu.
2. **`app`**: komendy palety „Zatrzymaj sesję” (skrót `x`) i „Respawn sesji”, oferowane według `actions`.

Nie robimy: „Usuń z listy” z potwierdzeniem, dialogu Mission Control i blokady menu przy nim (proponowane AM-412, „Kolejne etapy”); `⏎` attach (AM-505); `r` i `space` (AM-411); potwierdzenia przed stopem (pytanie 2); akcji dla wielu sesji naraz. Bez zmian `sessions:*`, `projects:*`, `command-palette:*`.

## Moduły

- `CHANGELOG.md` (`[Unreleased]`), `docs/ROADMAP.md` (linia AM-410 i nowa AM-412). Bez nowych bibliotek i bez ADR.

## Zmiany API

`sessions:api`, `command-palette:api`, `projects:*`: brak. Publiczne API `mission-control:ui` (wywołuje tylko `app`):

```kotlin
public sealed interface MissionControlIntent {
    // NextSession, PreviousSession, SelectFilter bez zmian
    /** `x` and the palette: stops the selected visible session when it is active; otherwise ignored (FR-S4). */
    public data object StopSelected : MissionControlIntent
    /** Palette and panel: respawns the selected visible session when it is not active; otherwise ignored. */
    public data object RespawnSelected : MissionControlIntent
}

/**
 * Which session actions apply to the selected visible session now; both false without one and while
 * an action runs. `app` offers palette commands by it; the controller checks again when it runs one.
 */
public data class SessionActionsState(val canStop: Boolean, val canRespawn: Boolean)

/**
 * Constructor change: [sessions] is the whole `SessionsApi` (monitor for the list, commands for the actions),
 * and [logger] logs actions with session ids and fixed categories only (ENG-C8).
 */
@Suppress("LongParameterList") // tick is a test seam; see plan, question 3
public class MissionControlController(
    sessions: SessionsApi, projects: ProjectsApi, selectedProject: StateFlow<ProjectId?>,
    clock: Clock, scope: CoroutineScope, logger: Logger, tick: Duration = 1.seconds,
) {
    /** Actions of the selected visible session, for the palette (AM-410). */
    public val actions: StateFlow<SessionActionsState>
}
```

Wewnętrzne:

- `internal enum class SessionAction { STOP, RESPAWN }`; `internal data class ActionUi(val busy: Pair<SessionId, SessionAction>?, val failure: Failure?)`; `internal data class Failure(val id: SessionId, val action: SessionAction, val reason: UiText)`. Piąty strumień w `combine` kontrolera.
- `internal object SessionActions { fun target(sessions: List<Session>, selection: Selection): Session?; fun available(state: SessionState, busy: Boolean): Set<SessionAction> }`. `target` stosuje te same reguły co reduktor: sesja zaznaczona, w wybranym projekcie i widoczna przy filtrze.
- `internal class SessionActionRunner(commands: SessionCommands, logger: Logger) { suspend fun run(action: SessionAction, id: SessionId): UiText? }` (`null` = sukces), wzorem `ProjectCommands` z AM-305. `internal object SessionActionMessages { fun reason(error: SessionError): UiText; fun category(error: SessionError): String }`.
- `SessionDetails` dostaje `actions: Set<SessionAction>`, `busy: SessionAction?`, `failure: Failure?` (tylko gdy dotyczy tej sesji). `MissionControlEvent.Run(action)` dla kliknięć w panelu.
- `app`: `AppShortcuts.STOP_SESSION = Shortcut.of(chord('x'))`; `sessionCommands(projects, menu, actions: SessionActionsState, onIntent, openPalette)`; `AppCommands` łączy `projects.projects`, `controller.menu` i `missionControl.actions`.

### Decyzje

1. **Dostępność akcji** (tabela 1): sesja aktywna (`isActive`: Pracuje, Czeka na odpowiedź, Prosi o zgodę) → tylko „Zatrzymaj”; nieaktywna (Gotowe, Błąd, Zatrzymana) → tylko „Respawn”. Przyciski niedostępnej akcji nie są pokazywane. Nieaktualny snapshot (`Stale`) nie blokuje akcji: błąd z `SessionCommands` wraca jako komunikat.
2. **Cel akcji czytany na świeżo** (lekcja „stan po `stateIn` o krok w tyle”): `onIntent` liczy cel z `sessions.monitor.snapshot.value` i bieżącego `selection.value` przez `SessionActions.target`, nigdy ze `state.value` ani z `actions`. `j`, a zaraz po nim `x`, zatrzymuje nową sesję.
3. **Współbieżność**: jedna akcja naraz w kontrolerze. `busy` jest ustawiane w tym samym wywołaniu co `scope.launch` (jak `begin` w `ProjectsController`), więc drugie kliknięcie albo `x` przed startem korutyny jest ignorowane. W trakcie: przyciski wszystkich sesji wyłączone, `actions` = (false, false), panel sesji pokazuje „Zatrzymywanie…” / „Respawn…”. Zmiana zaznaczenia w trakcie jest dozwolona; akcja kończy się dla swojego `id`.
4. **Błędy**: bez dialogu. `Failure` pokazuje się w panelu tylko dla swojej sesji: tytuł `action.stop.failed` / `action.respawn.failed` i powód z `SessionActionMessages.reason` (tabela 2). Teksty są stałe, bez id, nazwy i ścieżki. `Failure` znika przy następnej akcji i przy zmianie zaznaczonej sesji (klik, j/k, zmiana projektu). Sukces nie ma komunikatu: nowy stan widać w liście, bo `SessionCommands` publikuje go przed powrotem.
5. **Logi**: INFO `session stopped` / `session respawned` z `sessionId`; WARN `session stop failed` / `session respawn failed` z `sessionId` i `reason` (kategoria z tabeli 2). Nigdy nazwa, `cwd`, podsumowanie ani pytanie agenta.
6. **Komendy palety** (grupa `SESSION`):

   | Id | Tytuł | Skrót | Warunek | Akcja |
   | --- | --- | --- | --- | --- |
   | `sessions.stop` | Zatrzymaj sesję (`keywords = [stop]`) | x | brak dialogu, `canStop` | `StopSelected` |
   | `sessions.respawn` | Respawn sesji (`keywords = [respawn, wznów]`) | – | brak dialogu, `canRespawn` | `RespawnSelected` |

   `x` działa tylko bez otwartego dialogu i bez otwartej palety: przy `menu.dialogOpen` `sessionCommands` zwraca pustą listę, a przy otwartej palecie `onChord` niczego nie uruchamia (AM-409). Gdy komenda `x` nie jest na liście (np. lista jest o krok w tyle), klawisz przechodzi dalej bez skutku.
7. **Panel szczegółów**: rząd przycisków pod stanem sesji: „Zatrzymaj  x” albo „Respawn” (tagi `missionControl.details.stop`, `.respawn`), potem `.busy` albo `.failure`.

## Ryzyka i pytania

Pytania blokujące: 1 (podział i zmiana zakresu względem roadmapy). Pozostałe w odpowiedzi do lead'a.

- **Rozmiar** (linie netto w `src/main`, bez importów, KDoc i pustych): `mission-control:ui` ~185 (kontroler 45, reguły 15, runner i komunikaty 50, typy stanu i reduktor 25, widok panelu 40, intencje i `SessionActionsState` 10); `app` ~35 (`sessionCommands` 20, `AppCommands`/`MainWindow`/skrót 15). Razem ~220, z zapasem 30% ~285; zasoby osobno ~16 linii. Cały AM-410 z „Usuń” i dialogiem: ~315, z zapasem ~410.
- `actions` to `stateIn` nad `stateIn`, a lista komend idzie jeszcze przez rejestr na `Default`. Komenda `x` może pojawić się kilka milisekund po zaznaczeniu. Kontroler i tak sprawdza cel na świeżo (decyzja 2), więc najgorszy skutek to `x` bez efektu.
- `FakeSessions` kończy komendy od razu; test „w toku” wymaga `GatedCommands` w testach modułu.
- Mapowanie `SessionError` → kategoria powiela `StopMessages.category` z `projects:ui` (moduły `ui` nie widzą się nawzajem). Wspólne miejsce wymagałoby zmiany `sessions:api`, poza zadaniem.
